Tensions found in the specification

  • LAN access versus no admin rights. Accepting connections from other computers normally needs a Windows Firewall inbound rule, which usually needs an administrator once. This is likely the one unavoidable admin step. See Q18.
  • One mode per mission versus nighttime as a core capability. Night images will appear in any general-traffic mission. I propose night handling as a cooperating algorithm inside the mode (DER-03). See Q8.
  • Changed files versus never invalidating earlier results. Resolved by treating each content change as a new source version that keeps its own results; earlier versions and their corrections remain. Whether originals are copied into an evidence store is Q7.
  • Training on the 16 GB / CPU-only profile. Detector fine-tuning may be impractical there. The design declares learning adapters per profile instead of promising them everywhere. See Q25.

Update 24 Oct · first sample reviewed Sample: Fintraffic camera C04507 preset C0450701 (Road 3 Tampere, Lakalaiva, Finland), 143 JPEGs over 24 h, CC BY 4.0. Findings that change the design:
  • Filename pattern differs from the spec. Names are C0450701_20261021T071528Z.jpg: camera-preset id, then ISO-8601 basic UTC with seconds. The spec's DDMMYYYY-HHmm-suffix did not appear. The parser becomes a configurable set of named patterns with declared precision (minute or second), and the preset id is a strong hint for view grouping.
  • All 1280×720 baseline JPEG, no EXIF, 143 unique checksums. Regular 10-minute interval with one 20-minute gap.
  • Night frames are monochrome. Vehicle colour must be reported as not observable at night for this camera type.
  • A burned-in caption sits at top-left; it is excluded from analysis by a default exclusion region suggestion.
  • Finland (Europe/Helsinki) is not among the four target countries; this sample is used for format, view and night-pipeline work, not plate or country evaluation.

Architecture and per-mission data model

One backend process on the workstation supervises a small set of worker processes. The browser is only a client. All state lives in a control database plus one database per mission. Proposed throughout unless marked.

SQLite justification and safeguards One operator, one host and per-mission isolation fit SQLite well, and it needs no service or admin rights. Safeguards: a single writer per mission database (the backend's writer task receives batched results from workers over a queue, so workers never hold write locks); WAL mode with synchronous=FULL for decisions and corrections; PRAGMA integrity_check on open; online backup API for scheduled and pre-upgrade backups; schema version table with forward-only migrations run only after a backup. A client-server database would only be justified if concurrent multi-user editing becomes a requirement.

Process and task model

  • Jobs are rows in control.db with state, priority class (interactive, operational, background), mission id and checkpoint. The scheduler survives restarts by resuming jobs from their checkpoints.
  • Workers are separate OS processes started on demand and stopped after idle time, so a model crash cannot take down the UI and model memory is returned to the system.
  • Priority: interactive requests (thumbnails, crops, review saves) are served by the backend directly; operational inference runs at normal priority; training at below-normal process priority and pauses at checkpoints when operational work queues.
  • Idempotency: each work item is keyed by (run, source version, stage). Re-delivery after a crash overwrites only uncommitted output.

Key rules encoded in the model

  • Timestamp parsing Confirmed: 17052026-1604-dcincincifbvhubuhbv → capture_utc = 2026-05-17T16:04Z, capture_precision = minute, suffix stored verbatim. Invalid dates such as 31022026 are rejected as malformed, never coerced.
  • Local time is computed when needed from capture_utc and iana_zone, never stored as the source of truth. Example: Asia/Jerusalem gives 19:04 on 17 May 2026 (summer) and 18:04 for the same clock time on 17 Jan 2026 (winter). These examples will become unit tests and are not yet executed.
  • Schedule boundaries Proposed: windows are half-open [start, end) in local wall-clock time. A minute-precision capture is inside when its whole minute lies inside the window. Local times that do not exist (spring-forward gap) cannot occur in captures because captures are UTC; window edges falling in a gap snap to the first valid instant, and repeated hours in autumn are matched in both occurrences. All four cases are listed in the test plan.
  • Region membership Proposed: an object counts as inside when its bounding box bottom-centre point (approximate ground contact) is inside at least one inclusion polygon and inside no exclusion polygon. Exclusion wins. No inclusion polygon means the whole frame is included. The membership rule is selectable per view (bottom-centre, centroid, overlap fraction) and recorded on the run.

05

Camera-view and nighttime-detection design

Camera-view grouping

Goal: group images by physical view so that different lighting of the same view stays one group, while different angles of the same camera become separate groups. Proposed

  1. Structural signature. For each image, compute a downscaled, illumination-normalized representation focused on fixed structure: gradient-orientation maps and local keypoints. Optionally add a learned image embedding (candidate: DINOv2 small, license to verify) compared against the classical baseline in Deliverable 06.
  2. Clustering. Density-based clustering on signatures within the mission, conservative so that uncertain images remain unassigned rather than forced into a group.
  3. Geometric verification. Before two clusters are merged, match keypoints between their representatives and fit a homography with RANSAC; a high inlier ratio with near-identity transform means the same view. This links day and night clusters where fixed structures (poles, signs, lane markings under lights) are visible.
  4. Operator confirmation. Proposals are shown as groups with representative images per condition, size and a confidence. The operator merges, splits, renames and reassigns. Day/night links the algorithm could not verify are shown as "possible same view".
  5. Ongoing assignment. New images are matched to existing views by signature plus geometric check. Below the acceptance score they go to an "unassigned" queue and are not analysed with any view's regions.

View-change detection

For each assigned image, the homography to the view reference is stored. If the estimated displacement at the region polygons exceeds a tolerance (operator-set, shown in pixels), or the match fails repeatedly over consecutive captures, the view enters needs review: its regions and background models are not applied to new images until the operator confirms, redraws or creates a new view. The tolerance has no preset value; it will be chosen from measured jitter on your samples.

Background and persistent lights (stills)

  • Built per view and per measured condition from many images, not from one reference. For each pixel neighbourhood the model keeps how often it is a light source and its typical brightness. Regions lit in a high share of images are persistent-light hypotheses.
  • Operator labels ("persistent background light") are authoritative and override the statistics.
  • Stopped vehicles (NGT-03): the model is fitted on a long time horizon and never updated from regions holding a current candidate or confirmed vehicle. A light that becomes frequent only recently is flagged "new persistent light?" for the operator instead of being absorbed automatically.
  • Wet roads and reflections: components below a light source and vertically elongated are scored as possible reflections; they reduce, not remove, candidate scores.

Light grouping

Pair hypotheses consider horizontal alignment, similar size and brightness, and spacing consistent with an expected vehicle width at that image row. The row-to-width map is learned per view from daytime vehicle detections in the same view, or from an operator-drawn lane width, so no physical distance is ever inferred from an unresolved light. Every group carries alternatives when ambiguous (for example "one vehicle with two lights" versus "two vehicles with one light each"), and the unresolved count reflects that ambiguity rather than picking one.

Video: one vehicle through three appearances

stateDiagram-v2
  [*] --> Unresolved: single bright region
  Unresolved --> Pair: region splits, centroid continuous

Tracks carry an appearance state. A transition is accepted only when position and motion are continuous and the new evidence contains the old (the pair sits where the blob was; the body box contains the pair). When two explanations fit, both track hypotheses are kept and marked "possible same vehicle"; event consolidation then produces one event with an ambiguity flag, never two silent duplicates. Gap limits and association thresholds are operator-visible parameters calibrated on your recordings.

Nighttime evaluation plan

  • Dedicated labelled set from your cameras, split by view and date, with labels at all three appearance levels and explicit "persistent light" labels.
  • Metrics: candidate acceptance rate (share of candidates operators confirm), false alarms per image, recall of operator-identified vehicles broken down by appearance state, count error for confirmed vehicles, and for video the duplicate-event rate across transitions.
  • Slices: view, condition (dusk, night, glare, rain if labelled), distance band, country.
  • Ablations: detector only; light analysis only; fusion; fusion with enhancement. Enhancement is kept only if it measurably helps, and it never adds independent evidence.

Benchmark protocol Proposed

Automatic training policy (structure only)

If enabled, the scheduler may start a training run when all configured criteria hold: a minimum of new eligible labels per affected class since the last run, labels spread over a minimum number of views and date blocks, a cool-down period since the last run, and an idle resource window. Runtime safeguards

  • Memory governor: monitors system available memory and per-worker resident size; on pressure it shrinks queues, pauses background training, then defers new work items. It never drops input; deferred items stay queued.
  • VRAM governor: models declare their VRAM need at load; the scheduler refuses to co-load beyond free VRAM and falls back to sequential loading.
  • Interactive first: review requests bypass the job queue; training checkpoints and pauses when operational work arrives.
  • No silent quality loss: any optimization affecting analysis (input resize, tiling, frame stride, FP16/INT8) is written to the run's preprocessing record and shown in the run summary.
  • Operator overrides: worker count, backend, frame stride and precision can be changed; the screen shows estimated RAM/VRAM impact from measured model footprints and warns when the override exceeds the profile.

Staging → offline transfer

  1. On the connected staging machine, build packs from a locked dependency list; download models and datasets only from approved sources and record their licenses.
  2. Run the full automated test suite on staging, then on an air-gapped test VM with networking disabled.
  3. Transfer packs by approved removable media; verify manifests on the target.

Install without admin rights Proposed

  • Unpack to a user-writable folder (default under the user profile, or a chosen data drive). No registry writes outside the user hive.
  • Start at logon via a per-user Task Scheduler task or Startup-folder shortcut; both work without admin. A Windows service (starts before logon) only if an administrator approves (Q18).
  • Localhost access works immediately. LAN access needs the backend to listen on the LAN interface and, in most configurations, an inbound firewall rule created once by an administrator.
  • No application login or password is used. The server binds to localhost by default. Optional LAN access has no authentication and is intended only for a trusted, closed network.

Updates and rollback

  • Each app version installs side by side; a small launcher points to the active version.
  • Before activation: stop workers at checkpoints, back up control.db and every mission database, run migrations, run a self-check. On failure, restore backups and point back to the previous version.
  • Mission databases, evidence, corrections and model history are never deleted or overwritten by an update. Model packs only add versions; the production pointer changes only through promotion.

Proving it is offline

Acceptance test on a VM with no network adapter and on the target workstation with outbound traffic blocked and logged: full workflow from install through training and export, with zero outbound connection attempts recorded.
